# Decisions & Assumptions

- **Valuing the outstanding (unrealized) portion in BDT.** The spec gives a per-realization exchange rate but no rate for FC that hasn't been realized yet. Added a small `SPOT_RATES` reference table (`src/selectors.ts`, USD 119.5 / EUR 129.0) and used it to convert `outstandingFC → outstandingBDT` for the interest calc, the KPI cards, and the "Total LC Exposure" chart. Realized tranches always use their own recorded `exchangeRate`.
- **"Total LC exposure" KPI/chart** = realized amount at its actual historical rate + outstanding amount at current spot rate, summed across all LCs. This is the most defensible single BDT figure for the whole book without inventing a second data model for daily FX history.
- **Status priority when a status is ambiguous:** `Realized` is checked first (outstanding ≈ 0 wins even if maturity is in the past or future), then `Overdue` (maturity passed), then `Due Soon` (≤7 days out), then `Open`. Matches the spec's ordering.
- **"Due Soon" window** is `0 ≤ daysToMaturity ≤ 7`, inclusive of maturity day itself.
- **Interest only accrues on `Overdue` LCs**, computed as simple interest (`outstandingBDT × 0.12 × daysOverdue/365`) from maturity to "today" — no compounding, no interest once realized (interest freezes/disappears the moment outstanding hits 0, which is the intended behavior of a real-time tracker rather than a ledger of historical accrual).
- **Units:** invented three plausible spinning/weaving/dyeing unit names for a textile group (`Apex Spinning Mills`, `Desh Fabrics & Weaving`, `Green Dyeing & Finishing`) since the spec didn't name real ones; 3 LCs per unit for a balanced demo.
- **Buyers/banks** are realistic-sounding retail/sourcing names and known correspondent/issuing banks (H&M, Zara/Inditex, Walmart, Target, Primark, Marks & Spencer, Carrefour, LC Waikiki; Standard Chartered, HSBC, Citibank, Commerzbank, BNP Paribas, Deutsche Bank, Woori Bank, ICBC) — illustrative, not references to real LC transactions.
- **The ~$8,000 "missed partial-payment clause" incident** is modeled as `ILC-2026-0142`: a $100,000 LC where $92,000 was realized long ago but $8,000 has sat outstanding and overdue for 210 days, accruing meaningfully in BDT despite the small principal — the case that motivated this tracker in the first place.
- **Dates** are generated relative to `new Date()` at load time (offsets in days), not hardcoded ISO strings, so Overdue/Due Soon/Open statuses stay correct whenever the demo is run, per the spec's instruction.
- **Sorting** in the Register is limited to maturity date and status (as specified); status sort orders by urgency (Overdue → Due Soon → Open → Realized), not alphabetically.
- **Maturity calendar** on the dashboard shows LCs with `0–30` days to maturity that are not yet fully realized, sorted soonest-first, with `Due Soon` rows highlighted.
- **Alerts** are generated only for `Overdue` and `Due Soon` LCs (the two states that need action); `Open`/`Realized` LCs produce no alert, matching the spec's two message templates.
- No routing library — a single `tab` state in `App.tsx` switches between the three screens. No auth, no persistence; refreshing the page resets nothing (there's no mutable state to reset besides UI selection).

## Real Excel field mapping (`New Microsoft Excel Worksheet (1).xlsx`)

The user supplied their actual LC register's 44 column heads. `types.ts`/`sampleData.ts` were rebuilt to carry every one of them, either as a stored field or a derived selector. Mapping and interpretation calls:

- **Stored on `LC`:** Entry Date, LC Open Date, Acceptance Date, Maturity Date, L/C No., LDBC/IDBC → `billType`, Unit, Value-$ → `lcValue`, Discount Status, L/C Issuing Bank, Branch, Location, Party Name → `beneficiary` (kept the existing field name to avoid touching every screen; UI label changed to "Party Name" in the Register and drawer to match the source term), Advising Bank, Responsible Person, Realization Person, Media, Remarks, Adv. Bank Reminder Date, Issu. Bank Visiting Date, Next Visiting Date.
- **Stored on `Realization` (one per tranche):** Realized Currency, Realized Date, Partial Realized Value → `amountFC`, Exchange Rate, FDD/Pay Order Date, SCB ERQ Build Up (C), Short/Over Value $ and @ BDT, Source Tax rate and BDT, Adjustment Date.
- **Derived, never stored** (consistent with the "never store derived values" rule): Maturity Month (`getMaturityMonth`), STATUS (`getStatus` — same engine as before), OVERDUE TENURE (`getDaysOverdue`), D/OD (`getDueFlag`), Total Realized Value / Total Realized Value @ BDT (already `getRealizedFC`/`getRealizedBDT`, summed across tranches).
- **Two interest schemes, both present in the sheet:** "OD Interest @ 12%" is the bank's full-tenure penal rate (the existing engine). "Overdue Tenure (Waiving 90 Days)" + "OD Interest @ 6%" is modeled as a second, negotiated recovery track — a 90-day grace period is waived off the overdue tenure, then 6% p.a. applies to the remainder (`getWaivedOverdueTenure`, `getConcessionalInterestBDT`). "OD Interest Received Date" is stored as `concessionalInterestReceivedDate` (left unset in all sample rows — none of the modeled cases have recovered concessional interest yet).
- **Duplicate "Exchange Rate" header** (columns AA and AF in the source) was consolidated into the single `exchangeRate` field on `Realization` — both instances price the same FX event for that tranche, so a second field would be redundant rather than meaningful.
- **"SCB ERQ Build Up (C)"** — SCB (Standard Chartered Bank) is the nominated bank for the group's Export Retention Quota account; modeled as 15% of each realized tranche (`scbErqBuildUpFC`), a plausible retention rate under Bangladesh Bank's ERQ scheme.
- **"Source Tax (.6%),(.7%)&(.25%)&(.50%)&(1%)"** — the AIT (advance income tax) rate withheld on export proceeds varies by product/category; sample data uses 0.6% for most tranches and 0.5%/1% on a couple to reflect that real variability, stored as a decimal `sourceTaxRate` per tranche.
- **LDBC/IDBC** modeled as a two-value enum (`'LDBC' | 'IDBC'`) since the header itself names exactly those two classifications.
- **Branch vs. Location vs. Advising Bank** are now three distinct fields (previously the demo folded the city into the `issuingBank` string) — Branch/Location describe the foreign issuing bank, Advising Bank is the local Bangladeshi correspondent bank that negotiates the LC.

## Multi-module platform (Ahmed Group AI Project)

The app was restructured from a single-purpose LC tracker into a module hub. `App.tsx` is now a thin shell: auth gate, module-selection state, shared `lcs`/`loans` state, and a header with a back-to-hub button. Each module owns its own internal tabs/create-flow as a self-contained component (`components/lc/LCTrackingModule.tsx`, `components/loans/LoanManagementModule.tsx`, `components/email/EmailGeneration.tsx`, `components/charges/BankChargePrep.tsx`), so adding a fifth module later means adding one card to `ModuleHub.tsx` and one component — the shell doesn't otherwise change.

- **All four modules are fully functional**, not placeholders, per explicit choice when this was scoped out — each has real (if intentionally lightweight) data, logic, and screens.
- **LC Tracking** is unchanged functionally, just moved into its own module component; it remains the most detailed module (per-tranche realization history, dual interest schemes, full Excel-field parity) since it was built first and most thoroughly.
- **Loan Management** models STL (Short Term Loan), UPAS (Usance Payable at Sight — deferred LC acceptance financing), OD (Overdraft), and EDF (Export Development Fund — Bangladesh Bank's USD refinance scheme for exporters) as one `LoanFacility` type rather than four separate types, since they share the same lifecycle (disbursement → outstanding → maturity/adjustment, same Active/Due Soon/Overdue/Settled status engine, same simple-interest-on-overdue convention as the LC tracker for consistency). It's deliberately lighter than LC Tracking — a single `outstandingAmount` field rather than a realizations sub-ledger — since facility repayment mechanics (partial adjustments, renewal) weren't specified; extending it to track a repayment history would be the natural next step if requested.
- Each rate is facility-specific (`interestRatePct` per instance) rather than one universal rate, since STL/OD/UPAS/EDF genuinely carry different real-world pricing (EDF is concessional ~4.5%, OD/STL are commercial ~10-12%) — hardcoding one rate the way the LC tracker does for its single 12% penal rate would have been wrong here.
- Two `EDF`/`UPAS` sample facilities carry a `linkedLcNumber` referencing an actual sample LC (mirroring how EDF/UPAS are drawn against a specific export LC in practice) — kept as sample-data realism even though Email Generation (see below) no longer reads loan data.
- **Bank Charge Preparation** computes an illustrative Bangladesh-market charge schedule (Advising Commission 0.10%, Negotiation Commission 0.20%, flat SWIFT/courier charges, 15% VAT on the commission-based lines only, per standard BD VAT treatment of bank service charges) against an LC's exposure value in BDT. Rates/amounts are editable per line so the tool matches whatever a specific bank actually charges, since real schedules vary by bank and negotiate over time. "Print Voucher" uses the browser's native `window.print()` — a `.no-print` CSS rule hides the app chrome and the editable schedule so only the voucher itself prints, with no PDF library required.
- The categorical 4-color palette for the Loan Management "Outstanding by Facility Type" chart (STL/UPAS/OD/EDF) was run through the dataviz skill's `validate_palette.js` validator (light mode, all-pairs) before use — `#2563eb` / `#d97706` / `#0d9488` / `#be185d` passes lightness, chroma, and contrast checks, with a borderline (WARN-band) CVD separation between OD and EDF that's mitigated by the chart's direct-labeled legend, consistent with the skill's guidance that a WARN there is only acceptable with secondary encoding.

## Email Generation — corrected to Mobile Bill Allowance letters

The first pass at Email Generation guessed its purpose (LC/loan overdue reminder emails) since none was specified at the time. The user then supplied the actual reference material — a real batch of historical correspondence (Israq Group → Bank Asia Ltd, Agent Banking Division, requesting monthly Mobile Bill Allowance disbursement from a company CD account to employees' bank accounts, 2021–2026) — and clarified that this is what the module is for. The LC/loan reminder version (`emailTemplates.ts`, the "Suggested Drafts" list, the standalone "Bank Letters" module it was briefly split into) was removed rather than kept alongside the corrected version, since the two didn't overlap in purpose and keeping both would just be dead weight pretending to be a feature. `EmailGeneration.tsx` now contains the letter generator directly; there's no separate Bank Letters module or card.

The letters share one fixed structure with a handful of variable fields, so the module is a form that fills in that fixed template rather than a generic document editor.

- **Extracted the 4 real Israq Group entities** and their CD account numbers from the letters (Israq Textile Mills Ltd / Israq Spinning Mills Ltd / Israq Rotor Spinning Mills Ltd / Israq Cotton Mills Ltd) into `letters/shared.ts` (later renamed/generalized when the Fund Transfer letter type was added — see below), along with the signatories seen across the letters and Bank Asia's fixed recipient block. These are the user's own company entities and their own bank account numbers on their own outgoing correspondence — not third-party data — so hardcoding them as selectable defaults in their own internal tool is the same as any accounting system storing a company's own account numbers.
- **Built a number-to-Taka-words converter** (`numberToWords.ts`, Indian/Bangladeshi lakh/crore numbering) and verified it byte-for-byte against all 25 distinct amounts across the pasted letters (e.g. 3278 → "Three Thousand Two Hundred Seventy-Eight Taka only") before wiring it into the template — this automates the one part of the letter that's easy to get wrong or tedious to write by hand.
- **Normalized inconsistencies in the historical letters** rather than reproducing them literally: hyphenation of compound numbers is always applied ("Twenty-One", not the originals' inconsistent "Twenty One"), the subject line always includes "for {Month}- {Year}." (their more recent convention; some older letters omitted it), and the amount-in-words parenthetical always includes "Taka" (a few older letters just wrote "only"). The letters vary in wording across 5 years of real use; the template picks the most recent/complete convention as the standard going forward.
- **The one-off "single employee" letter** (Md. Ripon Mia, supplementary TK. 300 credited to his own account rather than "employees' respective accounts") is modeled as a distinct `Bulk` vs `Single Employee` mode rather than a special case bolted onto the regular template — the original's wording for that scenario was internally inconsistent (paragraph 2 still said "employees'" plural), so the single-employee body/enclosure text here is rewritten to be grammatically self-consistent while preserving the same intent (disburse a specific amount to one named employee's specific account).
- **Reference number** (`{PREFIX}/HO/{YYYY}-{MM}/{seq}`) is auto-suggested from the entity + letter date but the serial segment is a plain editable text field — the historical numbering isn't a clean per-entity or per-month counter (prefixes and serial ranges vary across the real letters), so exact continuation has to be a human judgment call, not something the tool can safely infer.
- **Print/PDF**, per explicit requirement, reuses the same proven pattern as Bank Charge Preparation: a `.no-print` rule hides the app header and the input form, `window.print()` triggers the browser's native print/Save-as-PDF dialog, and the letter body itself is an editable `<textarea>` (so last-minute wording tweaks are possible) that becomes borderless plain text under `@media print` so it reads as an ordinary paragraph on the printed page, not a form field.
- Letter date defaults to today; the "Generate Letter" button (not a live-updating effect) rebuilds Ref No./Subject/Body from the current form fields on demand — an explicit regenerate step rather than a silent side-effect, so editing one field (e.g. correcting the amount after already tweaking the body wording) never wipes out a manual edit elsewhere.

## Email Generation — second letter type: Fund Transfer Request

The user supplied a second real batch of letters — inter-company transfer requests between the group's own CD accounts at Bank Asia — and was explicit that the module must never require the user to type or remember any account number, entity name, or boilerplate. Everything selectable comes from a dropdown; typing only ever happens for an amount and an optional serial number.

- **Account-level, not just entity-level, dropdowns.** Reading the letters closely showed the group doesn't have one account per entity — Israq Textile Mills Ltd alone appears with at least 4 distinct account numbers (a main CD account, a recurring "central/pooling" account that most transfers land in, and two others seen once or twice each). A single "pick the entity" dropdown (as Mobile Bill Allowance uses, since that letter type only ever references one account per entity) would have forced free-text account entry for the rest — exactly what was ruled out. So Fund Transfer introduces `letters/fundTransferTemplate.ts`'s `KNOWN_ACCOUNTS`: every distinct account number seen in the letters, each tagged with its owning entity and a plain-English label (e.g. "Israq Textile Mills Ltd. — Central/Pooling Account (1000000000002)"), and the From/To selects pick directly from that list. Selecting an account fills in the entity name, account number, and (via the From account) the reference prefix — nothing is retyped.
- **Extracted shared structure into `letters/shared.ts` and `components/email/LetterShell.tsx`.** Once a second letter type existed, the entity list, signatory list, recipient block, and month names were genuinely reused (not speculatively) across two templates, and the print-letter chrome (date/ref/recipient/subject/body/signature block, the Print button, the `.no-print`/`@media print` rules) was identical in structure between the two, differing only in the closing line and whether there's a footer. Both were pulled out at this point — this wasn't done pre-emptively when only one letter type existed, since a single call site doesn't justify an abstraction.
- **Entity naming differs by letter type** ("Israq Textile Mills **Limited**" in Mobile Bill Allowance letters vs "Israq Textile Mills **Ltd.**" in Fund Transfer letters) — this is how the group's own historical letters actually differ, not an inconsistency to paper over, so `GroupEntity` stores both a `name` (full) and `shortName` (abbreviated) and each template uses the one that matches its own letters.
- **"Lac" vs "Lakh".** `numberToWords.ts` originally spelled the 100,000 unit "Lakh"; every Fund Transfer letter that crosses that threshold spells it "Lac" instead (Mobile Bill Allowance amounts never got that large, so this never surfaced there). Renamed the converter's output to "Lac" globally, since that's the group's own established spelling and nothing contradicts it.
- **Ref format gained a category segment**: Fund Transfer letters are `{PREFIX}/HO/FT/{YYYY}-{MM}/{seq}` vs Mobile Bill Allowance's `{PREFIX}/HO/{YYYY}-{MM}/{seq}` — `suggestReference()` in `shared.ts` takes an optional `category` argument to cover both without duplicating the function.
- **Third signatory variant added**: "Sajid Israq" signs as both "Director" (most letters) and "CEO" (one letter) across the two letter types, and "Md. Fazlul Hoque" signs in parentheses — `(Md. Fazlul Hoque)` — while Sajid Israq never is; `Signatory` now carries an optional `parenthesize` flag rendered by `LetterShell` instead of baking the parentheses into a name string.
- **No enclosure/footer line** for Fund Transfer (unlike Mobile Bill Allowance's "Enclosed list of employees…" line) — `LetterShell`'s `footer` prop is simply omitted, since these letters don't reference an attached list.
- **Closing line differs**: Mobile Bill Allowance ends "...appreciated.\nThanking You." (one paragraph, line break); Fund Transfer ends "...appreciated." then a separate paragraph "Best regards." — passed into `LetterShell` as a `closing` ReactNode slot per letter type rather than a text template, since the two aren't just word substitutions of each other (different spacing/structure).

## Dummy account numbers

All real CD account numbers were replaced with placeholders (`letters/shared.ts`'s `GROUP_ENTITIES`, `letters/fundTransferTemplate.ts`'s `KNOWN_ACCOUNTS`) — a simple per-entity ascending scheme (ITML `1000000000001/2/3`, ISML `2000000000001`, IRSM `3000000000001`, ICML `4000000000001`, plus ITML's shorter "Other Account" as `00000000009`) that preserves each account's original digit length so the generated letters still look like real bank correspondence, while making clear at a glance that none of the numbers are genuine. Each entity's `-main` account in `KNOWN_ACCOUNTS` intentionally matches its `cdAccountNo` in `shared.ts`, since both represent the same underlying account across the two letter types. Company/person names (Israq Group entities, Sajid Israq, Md. Fazlul Hoque) were left as-is — only account numbers were flagged as needing to be dummy.

## Yarn Costing & Profitability Analytics — full rebuild (replaces the original Yarn Costing module)

The original Yarn Costing module (a single costing-sheet calculator — fiber blend → wastage → cost/kg → margin) was explicitly superseded by a much larger spec: a 13-screen daily-closing ERP workflow covering production, raw material, wastage, costing, sales, variance, profitability, monthly trends, reports, master data, and alerts. Per the user's instruction, the old module was deleted outright (`costingSelectors.ts`, `sampleCostingSheets.ts`, `components/costing/*`) rather than kept alongside the new one — same reasoning as the Email Generation replacement above: the two didn't overlap in scope, so keeping the old one would just be dead weight. The new module lives under `src/yarnCosting/` (domain layer) and `src/components/yarnCosting/` (13 screens + shell), self-contained — it doesn't share state with any other module.

**Currency.** The request said "in $USD" but every single worked example in the same message used ৳ (Taka) figures, and the dedicated "Exchange Rate Impact" section is explicitly about USD-denominated imported cotton converting to BDT. Treated as BDT-primary (consistent with every other module in the app) with cotton purchase priced in USD where realistic (imported lots) — the "$USD" phrase is read as referring to that cotton-import pricing, not the module's reporting currency.

**Data model** (`yarnCosting/types.ts`): `DailyYarnRecord` (one per yarn per day — production, WIP, machine hours/downtime, cotton blend, per-process wastage, electricity/labor/maintenance/depreciation/overhead/packing/finance costs), `DailySalesEntry` (one per sale — a day can have multiple, across yarns and customers), and `DailyClosing` (one per date — status/checklist/prepared-reviewed-approved metadata). This is a deliberate simplification from the spec's implied separate Production/RawMaterial/Wastage/Cost/Sales entities: since they're all captured together for the same yarn on the same day, splitting them into five parallel arrays keyed by (date, yarnId) would only add join complexity without adding real flexibility — sales alone stay separate since one yarn can have several sales orders per day.

**Core costing engine** (`yarnCosting/calculations.ts`):
- **Compounding multi-process wastage.** Fiber passes through every process in the route (Blow Room → Carding → [Pre-Combing → Combing, combed only] → Drawing → Ring Frame → Winding) losing its own actual% at each step, so `getProcessStages` walks the route forward from a nominal 1kg input and scales so the *output* lands on exactly 1kg of finished yarn — giving both the true raw-fiber input ratio per kg of yarn (compounded, not just summed) and a genuine per-process waste quantity/value for drill-down, not just an aggregate wastage %.
- **Fixed-vs-variable cost split matters, especially for the scenario tool.** Raw material and packing scale per kg (rate stays constant); labor, maintenance, depreciation, and factory overhead are fixed for the day's run (same shift cost regardless of yield) — so a drop in efficiency should raise their cost/kg by spreading the same total over fewer kg. `runScenario` models this explicitly (recomputing each fixed total ÷ new output) rather than mutating a `DailyYarnRecord` and re-running `getCostBreakdown`, which would incorrectly treat every cost as variable.
- **Weighted-average inventory/COGS, not "cost = today's production."** Per section 13's explicit requirement: `buildInventoryLedger` walks each yarn's records chronologically, carrying opening/closing kg and value forward, so COGS is tied to what was actually *sold* on a given day (at that day's weighted-average available cost), while unsold production sits in inventory value instead of being expensed. This is why "yesterday" (the pending Draft day) correctly shows zero COGS/revenue for every yarn — no sales have been entered for it yet, which is also exactly the scenario the Daily Closing checklist is built to catch.
- **Estimated cost standards are internally consistent with the master data, not independently chosen.** An early build set `standardWastagePct` to just the Combing process's own 15% standard, and picked `rawMaterialPerKg` illustratively — but the *actual* compounded overall wastage for the combed route (compounding all 7 processes) is ~22.8%, not 15%, and the real weighted fiber cost from the chosen cotton-lot blend was ~277-280/kg, not the illustrative 310-318. That mismatch produced nonsense: false "cost exceeded standard" alerts and a slightly *negative* overall margin for 30/1 Carded purely from bad reference numbers, not real operational drift. Fixed by deriving `standardWastagePct` from compounding `WASTAGE_STANDARDS` per route and `rawMaterialPerKg` from the actual `COTTON_LOTS` blend, verified with a runtime sanity script before building any UI on top. Every "Estimated vs Actual" variance in the app now reflects genuine operational movement, not a data-entry mismatch between two independently-guessed numbers.
- One yarn (30/1 Combed) is deliberately left on a thinner margin (~8%, vs ~12-13% for the others) as the one "needs attention" case — consistent with every other module's pattern (the $8,000 overdue LC, the overdue loan facilities, the loss-making yarn count) of always including a real problem alongside the healthy cases rather than an all-green demo.

**45-day sample dataset** (`yarnCosting/sampleDailyData.ts`), 4 yarns (30/1 & 40/1, Carded & Combed) × 45 days, generated via a seeded PRNG (mulberry32, `yarnCosting/rng.ts`) rather than `Math.random()` — a demo whose KPIs/charts reshuffle on every reload would undermine being shown or discussed consistently. Specific engineered scenarios on "yesterday" (the pending day): 30/1 Combed gets a genuine efficiency dip (below standard) plus 5+ hours of downtime (Machine Breakdown), and 40/1 Combed gets a Combing-process wastage spike — both surface as real alerts, not just random noise. Sales are deliberately *absent* for yesterday across all yarns, so the Daily Closing checklist's "Sales entered" item starts unchecked and Submit is genuinely blocked until the accountant enters them — this is what makes the core user journey (section 39) actually demonstrable rather than pre-completed.

**Reference data invented for this module** (no source document existed): 5 cotton lots (USA/Brazil/Australia/Uzbekistan/Domestic, each with a full landed-cost breakdown — purchase price, freight, insurance, C&F, port, customs, bank, transport), 5 yarn-trading customers (distinct from Email Generation's Israq Group entities and from LC Tracking's export buyers, since a spinning mill's yarn customers are other domestic knitting/weaving mills, not export retail brands), and an exchange-rate history trending toward the same USD/BDT rate (119.5) already used in `selectors.ts` for LC Tracking, for cross-module consistency. Cotton import LC/PI references use a distinct `ILC-IMP-*` numbering rather than reusing LC Tracking's sample export LC numbers — an import LC (buying raw cotton) and an export LC (selling finished goods, what LC Tracking models) are different instruments in opposite directions; reusing the export numbers would have implied a false cross-reference.

**Scope decisions:**
- "Yarn Count Analysis" (spec section 19) and "Product-wise Profitability" (section 17) are the same table in this app, since each `Yarn` entity already *is* a unique count+type combination (30/1 Carded, 40/1 Combed, etc.) — modeling them as separate screens would just duplicate the same query.
- "Main Dashboard" (14/15) and "Executive Dashboard" (37) were merged into the single "Dashboard" tab — the canonical 13-item sub-navigation the user specified doesn't list an Executive Dashboard as a separate item, and the two describe near-identical content (KPIs, trend, top/bottom performers, alerts) at different altitudes. The Dashboard tab includes both operational KPIs and the executive-framed Top Performing / Loss-Risk / Management Alerts panels.
- **Role-based access is conceptual, not enforced auth** — there's no backend and only one demo login for the whole app. A `Role` selector in the module's top bar (Accountant/Production Manager/Sales/Accounts Manager/Management) gates which workflow buttons are enabled on the Daily Closing screen (Submit needs Accountant/Accounts Manager; Approve needs Accounts Manager/Management *and* a completed review step), demonstrating the access-control shape without pretending to be real security.
- **Cost composition and cost-variance drill-downs use plain ranked bar lists / stepped waterfalls, not multi-color pie charts.** With 7 cost components, a categorical pie needs 7 mutually-distinguishable hues — hard to validate and harder to read at a glance — where a single-hue ranked list (sorted by contribution) communicates the same "where does the money go" insight more clearly, consistent with the brief's "prioritize insight over decorative visuals."
- The Revenue/Cost/Profit trend line chart's 3-color palette (`#2563eb` blue / `#d97706` amber / `#10b981` emerald) was run through the dataviz skill's validator (light mode, all-pairs) before use — the first candidate (blue/slate/emerald) failed the chroma-floor check (slate reads as gray, not a real hue), so slate was swapped for amber.

## LC Scrutiny (6th module)

Modeled as the step that happens *before* LC Tracking — verifying an LC's clauses against the PI (financial, banking, shipment, payment, compliance) and raising discrepancies — rather than a standalone island. It lives under `src/lcScrutiny/` (domain) and `src/components/lcScrutiny/` (Dashboard/Register/Alerts + a create form), cross-referencing LC Tracking's existing `lcs` data (passed in read-only, same pattern as Bank Charge Preparation and Loan Management) so a new checklist can be created by picking an existing LC and having its LC Information/Banking fields auto-filled, rather than re-typed.

- **Applicant vs. Beneficiary, corrected.** LC Tracking's `LC.beneficiary` field actually stores the *buyer* (e.g. "H&M Hennes & Mauritz GBC AB") — a naming quirk already flagged in the Excel-mapping notes above, kept as-is there to avoid a wide rename. The user's checklist spec correctly asks for both **Applicant (Buyer Name)** and **Beneficiary Name** as distinct fields, so LC Scrutiny gets this right: `applicantName` maps from `LC.beneficiary` (the buyer), and `beneficiaryName` is the group's own exporting entity, resolved from the LC's operating `unit` via a small `BENEFICIARY_BY_UNIT` map (Apex Spinning Mills → Israq Spinning Mills Limited, Desh Fabrics & Weaving → Israq Textile Mills Limited, Green Dyeing & Finishing → Israq Cotton Mills Limited) — reusing the same Israq Group entity names as Email Generation's `GROUP_ENTITIES`, for a consistent legal-entity taxonomy across modules.
- **Discrepancy engine** (`lcScrutiny/discrepancyEngine.ts`) directly implements the ask ("if any discrepancy exists: raise an alert") across six categories: **Financial** (LC value/quantity vs. PI value/quantity, outside the recorded tolerance %, severity escalating to critical beyond 2× tolerance), **Shipment** (planned shipment date after the latest-shipment-date clause; and — per UCP 600 Art. 14(c)'s standard 21-day default — too little gap between latest shipment date and LC expiry to present documents), **Payment** (payment terms mentioning "sight" alongside a nonzero payment duration; a blank partial-payment clause; a partial-payment clause that contradicts "partial shipment not allowed"), **Banking** (blank charging-heads or reimbursement-instructions clauses), **Documents** (any required document not yet received), and **Compliance** (missing Beneficiary BIN; any non-blank Restricted Clause, always critical, since a restricted clause is inherently a risk item needing management sign-off).
- **A real regex bug caught during verification**: the partial-payment consistency check first used `/partial/i.test(...)`, which matched the *negation* wording too ("Not applicable — partial shipment not allowed" contains "partial"), producing a false positive on a checklist meant to be Clean. Fixed to `/partial\s+payments?\s+accepted/i` — matching only the affirmative phrasing that would actually be inconsistent with partial shipment being disallowed. Caught by the same runtime-verification habit used for Yarn Costing's estimated-standards bug: compute the sample data through the real engine and check the result matches intent before building UI on top, rather than trusting the wiring is right.
- **Sample data doubles as narrative continuity with LC Tracking.** ILC-2026-0142 (H&M) — the LC with the ~$8,000 realization dispute already tracked in LC Tracking's sample data — gets a scrutiny checklist with its **partial payment clause left blank**, flagged as a Payment discrepancy at the time of LC opening. The remark spells out the connection: the gap identified (and, in this demo, not fully chased down) at scrutiny time is what later surfaced as the real payment dispute. This is deliberate, not incidental — it demonstrates exactly the value proposition of a scrutiny module ("if we'd caught this here, we could have avoided the dispute downstream"), using data the app already had rather than inventing an unrelated example. The other five sample checklists (2 Clean, 3 more Discrepancy Found across Financial/Shipment+Documents/Compliance) all link to real LC Tracking sample LCs the same way.
- **No draft/submit/approve workflow**, unlike Yarn Costing's Daily Closing — the user's spec for this module describes verification and alerting, not a multi-step approval chain, so a checklist is either being drafted in the create form or saved (with its status — Clean / Discrepancy Found — always freshly derived from its data, never stored) rather than modeled as a lifecycle with lock states. Building an approval workflow here would have been solving a problem the spec didn't ask for.
- **Cost composition-style category chart avoided** for "Discrepancies by Category" in favor of the same single-hue ranked bar list used in Yarn Costing's cost breakdown — six categories would need six mutually-distinguishable categorical hues to validate properly, where a ranked list communicates "which category has the most problems" at a glance without that overhead.
